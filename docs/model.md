# LCAD engineering model (schema v0 draft)

The model is the product. Every output is a function of it [M1], and the integrity guarantees in
[`integrity.md`](integrity.md) depend on how it stores facts. This document is a **draft**: Phase 0
writes one real, already-built cabinet in this format by hand, and the schema changes until that
cabinet can be expressed completely and naturally ([ADR 0002](decisions/0002-first-slice-reconstructs-a-built-cabinet.md)).

## 1 Principles

1. **Store each fact once; derive the rest** [M3]. A device's cabinet is stored only as its
   `location`. The BOM "location" column, the per-cabinet device list, whether a wire is internal or
   an interconnect, sheet cross-references, I/O addresses and contact cross-references are all
   computed at build time. This single choice removes most change-propagation problems: moving a
   device changes one field and every derived view follows.
2. **Relationships are by ID, never by tag or sheet number** [M2]. Tags and sheet numbers are labels
   that change; IDs do not.
3. **Logical and physical are different objects** [M4]. A potential (`+24V-CTRL`) is logical; a
   conductor (a specific piece of wire with a size and colour) is physical.
4. **Engineering, composition and output are separate.** `design/` holds what is connected to what;
   `layout/` holds where things are drawn and placed; `artifacts/` holds generated files.
5. **Explicit units and frames** [M5]. Lengths in mm unless a field says otherwise; every placement
   names its coordinate frame.

## 2 Identity and units

- **ID format:** a type prefix plus a short random suffix: `dev_7Q2M`, `cnd_00A1`, `pot_4KDT`,
  `loc_CAB1`, `cbl_91XZ`. Generated by LCAD, never reused, never derived from a tag [M2].
  Readable location IDs (`loc_CAB1`) are allowed because locations are few and stable; they are
  still never renamed when the cabinet's label changes.
- **Tags** follow the project's tag scheme (IEC 81346-style `=Function+Location-Device` or the
  user's own), set in the project's conventions ([`conventions.md`](conventions.md)), not in code [C3].
- **Pins** are identified by the manufacturer's terminal designation from the part record. A pin
  reference is `{device, pin}`; a terminal-block level is `{device, terminal, level}`.
- **Geometry never implies connectivity** [M5]: two parts touching in 3D, or a symbol drawn on a
  line, are not connected unless a conductor, bridge or busbar object says so.

## 3 Locations

A tree. Every device has exactly one `location`; everything location-dependent is derived from it.

```yaml
# design/locations.yaml
- id: loc_SITE
  kind: machine
- id: loc_CAB1
  kind: cabinet
  parent: loc_SITE
  label: "+CAB1"
  enclosure: dev_ENC1          # the enclosure is itself a device with a part number
- id: loc_CAB1_MP
  kind: mounting_plate
  parent: loc_CAB1
- id: loc_CAB1_DOOR
  kind: door
  parent: loc_CAB1
- id: loc_CAB2
  kind: cabinet
  parent: loc_SITE
  label: "+CAB2"
- id: loc_FIELD_INFEED
  kind: field_area              # devices mounted on the machine, outside any cabinet
  parent: loc_SITE
  label: "+INFEED"
```

Multiple cabinets and field areas exist from v0 [M9]; moving a device between them is the core
integrity case.

## 4 Devices, potentials and conductors

```yaml
# design/devices.yaml
- id: dev_7Q2M
  tag: "-K12"                   # label only
  part: lib:schneider/LC1D09BD@2  # pinned part version (see §5)
  location: loc_CAB1_MP          # the ONLY stored location fact
  supply_scope: by_us            # by_us | by_customer | by_others | existing   [I6]
  function: fn_CONVEYOR1         # optional link to architecture function
  requirement_refs: [req_014]
  plc: { lplc_type: null }       # optional LPLC block type [X3]

- id: dev_B101
  tag: "-B101"
  part: lib:ifm/IG5398@1
  location: loc_FIELD_INFEED
  supply_scope: by_us

# design/potentials.yaml
- id: pot_4KDT
  name: "+24V-CTRL"
  kind: dc
  nominal_v: 24
- id: pot_0VCT
  name: "0V-CTRL"
  kind: dc_return

# design/conductors.yaml — physical wires inside one location, or within a cable
- id: cnd_00A1
  from: { device: dev_PSU1, pin: "+" }
  to:   { device: dev_XT1, terminal: "1", level: 1 }
  potential: pot_4KDT
  wire_type: wt_18AWG_BU         # size, colour, insulation via type record
  bridge: false

# design/cables.yaml — multi-core cables, including interconnects between locations
- id: cbl_91XZ
  tag: "-W101"
  part: lib:lapp/OLFLEX-110-7G18@1
  ends:
    - { location: loc_CAB1, entry: ent_CAB1_A3 }   # cable entry position (see layout)
    - { location: loc_FIELD_INFEED }
  cores:
    - { core: "1", from: { device: dev_XT2, terminal: "4" }, to: { device: dev_B101, pin: "1" }, potential: pot_4KDT }
    - { core: "2", from: { device: dev_XT2, terminal: "5" }, to: { device: dev_B101, pin: "4" }, potential: pot_SIG_B101 }
    - { core: "GNYE", spare: true }
```

A conductor that would join two different locations directly is invalid [I7]; it must be a core of
a cable (or pass through a plug connector), so the interconnect has a part number, an entry
position and a place in the BOM.

**I/O channels** are not a separate list. A channel is a pin on an I/O module device; a channel
assignment is the conductor (or core) connecting it. The I/O list is derived.

**Safety functions** (`design/safety.yaml`) reference the architecture's safety function, its
required performance, the initiating devices, logic device, output devices and reset — as objects,
so the drawing philosophy can keep a function together [DP4] and the safety review can trace it.

## 5 Parts and library

```yaml
# components/ or shared library — one record per part version
id: lib:schneider/LC1D09BD@2
manufacturer: Schneider Electric
order_code: LC1D09BD
lifecycle: approved               # imported | proposed | verified | approved | deprecated
category: contactor
ratings: { coil_v: 24, coil_kind: dc, ie_ac3_a: 9 }
symbol_units:                     # how the device splits across sheets
  - { unit: coil,  pins: ["A1", "A2"] }
  - { unit: main,  pins: ["1","2","3","4","5","6"] }
  - { unit: aux,   pins: ["13","14"] }
terminals: { conductor_range_mm2: [1, 4], torque_nm: 1.7 }
geometry: { step: assets/sha256-…step, iso_svg: derived, footprint: { w: 45, h: 77, d: 86 } }
accessories_required: []          # e.g. end stops, bridges, markers; drives BOM [I5]
documents: [{ title: "Datasheet", rev: "2024-03", ref: "p.3" }]
supplier_refs: []                 # catalog numbers kept separate from manufacturer identity
```

Projects pin part versions; a library correction produces an impact report and never changes a
pinned project [M7]. Project-specific parts live in the project's `components/` indefinitely.

## 6 The project repository

Each machine project is its own Git repository, separate from the LCAD repository [M6]. Users do
not write code; LCAD edits these files through its UI, CLI and AI operations.

```text
machine-project/
  README.md
  lcad.project.yaml        # design basis: jurisdiction, standards editions [S4], customer requirements
  lcad.lock                # engine, schema, rule pack, library and tool versions
  requirements/            # briefs (originals) and requirements.yaml
  architecture/            # architecture objects + saved diagram layout
  design/                  # locations, devices, potentials, conductors, cables, safety, numbering.lock
  layout/                  # space estimate, placements, cable entries, sheets.yaml (sheet plan)
  components/              # project-specific part records and pinned references
  inputs/                  # manuals, quotes, CAD assets (manifest + LFS/artifact store)
  procurement/             # reference BOM, manual BOM lines, quotes, price snapshots
  profile/                 # conventions.yaml, sourcing.yaml, origin.yaml: copied from a profile, then project-owned [C1]
  reviews/                 # findings, decisions.yaml (exceptions), approvals bound to hashes
  artifacts/               # generated: web/, drawings/, bom/, cabinet/, automation/
  releases/                # immutable manifests: source commit, pinned versions, approvals, output hashes
  .lcad/cache/             # ignored
```

- **Canonical serialization** [M8]: sorted keys, stable list order (by ID), fixed float precision,
  so a diff shows the engineering change.
- **Large binaries** by content hash with a manifest (Git LFS or an artifact store). A checkout
  missing required assets is reported as incomplete, never silently rebuilt without them.
- **No silent upgrades** [M6]: opening a project never upgrades its schema, rules, library or
  engine; migrations are reviewable changes on a branch.
- **Approvals** are bound to the hash of the content they approve [W6]; copying or merging an
  approval file cannot approve changed content.
- **Reproducibility:** byte-identical output is promised only where it is demonstrated; otherwise
  outputs are tested for semantic and visual equivalence.
- **Redlines** from DXF or marked-up PDFs become *proposed* model changes; geometry edits are never
  reverse-engineered into wiring automatically.
- **Legacy static pages** (hand-drawn sheets brought in as-is) are registered with interface objects
  and flagged as lacking machine-checked connectivity.

## 7 Numbering

Wire numbers, terminal numbers and similar identifiers are what people write on the shop floor, so
they must be stable [M10]:

- The **numbering scheme** is a project convention (`profile/conventions.yaml`): domains and formats,
  e.g. the author profile's six-digit `AAGGSS` labels, one per potential, built from module and
  terminal for I/O (CV2, ADR 0009), or sheet.zone-based, or a counter per cabinet.
- A deterministic **allocator** assigns numbers to new objects only and records them in
  `design/numbering.lock.yaml`. Rebuilding never renumbers existing objects.
- **Drawing IDs** are allocated the same way (author profile: five digits `AATNN`, CV4) and locked
  in the same file; inserting a drawing takes the next free number in its area and type [D8].
- Once a revision is released, renumbering an object requires an explicit operation and shows in
  the change package.
- If the policy encodes location (e.g. a cabinet prefix), moving a device makes its numbers
  inconsistent with the policy; that is a finding with options (renumber or keep), not an automatic
  renumber ([`integrity.md` §3](integrity.md#3-typed-operations)).

## Open schema questions (Phase 0)

- Tag scheme: what the reference package uses, and whether tags are derived from location
  (`+CAB1-K12`) or independent.
- Busbars, bridges and jumper combs: conductor subtypes or their own objects.
- Terminal-strip modelling: one device per strip with levels, or one device per terminal block.
- Plug connectors in interconnects: a pair of devices plus a mating relation, or a single object.
- How much of the architecture view is a separate object set versus a projection of design objects.
